fix-ui · architecture · v1

Point at what's wrong.
Your coding agent fixes it.

How the pieces fit, what runs where, and what the agent is actually doing when you type fix ui.

Runs on your machine only Default port 127.0.0.1:3499 Inbox .fix-ui.jsonl
01

Four parts and one file

The file is the important one. Everything else exists to put lines in it, or to take lines out.

Two adapters share one core, so the picker behaves identically whichever way it arrives. The embed reaches every user of an app that ships it, including browsers with no extension installed. The extension reaches every site without shipping anything. Neither one talks to your filesystem — only the bridge does.

What a note actually looks like on disk

// ~/my-app/.fix-ui.jsonl — one line per note
{
  "v": 1,
  "note": "make this button bigger",
  "selector": "#pricing button.mt-5",
  "component": "PricingCard",
  "elementText": "Continue",
  "url": "http://localhost:3000/#pricing",
  "consoleErrors": [
    { "message": "TypeError: x is not a function", "count": 3 }
  ]
}

The selector alone would be brittle, so every entry carries three ways to find the same element: the CSS path, the framework component name, and the element's own text. If the page has changed since you wrote the note, the agent still has two other handles. Recent console errors ride along because the thing you're complaining about and the thing that's throwing are often the same thing.

02

The two directions

You start one of them. The agent starts the other. Both end with a human deciding something.

You → agent · the inbox
  1. 1
    You arm the pickerClick the floating chip, or the extension's toolbar button. Nothing is injected into any page until you do.
  2. 2
    You click an elementThe whole pointer sequence is suppressed, so the button you're pointing at doesn't fire. A popover opens.
  3. 3
    You type a note and saveThe picker builds the entry and POSTs it to the bridge. Bridge down? It queues and retries.
  4. 4
    The bridge appends a lineIt routes to the right project, strips the routing field, and appends to that project's .fix-ui.jsonl.
  5. 5
    You type "fix ui"The agent calls list_feedback — or just reads the file. Both work; the file is the contract.
  6. 6
    It fixes and clearsresolve_feedback(id) removes the line. No tombstone — the inbox is a queue, not a log.
Agent → you · the review
  1. 1
    The agent asks for eyesAfter changing UI it calls request_review. That call blocks. Its turn is suspended.
  2. 2
    The bridge holds it openIt doesn't answer yet. It pushes an event down the SSE stream your page is subscribed to.
  3. 3
    Your page wakes itself upBanner appears with the agent's prompt, picker arms itself. You never hunt for the chip.
  4. 4
    You look, and click aroundDrop notes on anything wrong. They're ordinary entries; the page remembers which ones are part of this review.
  5. 5
    You approve or request changesThe verdict POSTs back with the ids of the notes you left.
  6. 6
    The agent's call returnsIt resumes the same turn holding your verdict and your notes. Nothing was pushed at it — it was waiting.
Why the blocking call matters. An MCP server cannot start a conversation with an agent — tools are agent-initiated, always. So "the agent somehow knows what you clicked" is never a push. It's a call the agent made, suspended, and your click is the return value. Every part of this design follows from that one fact.
03

Where the bridge actually runs

On your machine, as a Node process, started one of two ways — and it works out for itself which one it is.

There is no server anywhere. The bridge binds 127.0.0.1 only, which means nothing outside your machine can reach it — not your network, not the internet. It stores nothing but the files already in your project.

The wrinkle is that it has two completely different callers. Browsers need HTTP. Agents need MCP over stdio. So one process serves both, and how it was started decides how it behaves.

What happens with three Claude Code sessions open

Each session spawns its own bridge process. They cannot all own port 3499, and you would not want three processes writing the same files. So they arbitrate:

The upshot: one daemon serves every project on the machine, and each session's own process makes sure its tool calls land against the right directory. You never think about it — but it's why the second session doesn't crash, and why you can have one browser tab open against two different projects.

04

What you need installed

Node is required — the bridge is a Node process. Where it's required depends on which half you mean.

To do thisNodepnpmChromeNotes
Run the bridge yes—— Node 20+. It is a Node process; there is no way around this one.
Use the Chrome extension yes—yes The extension itself runs inside Chrome and needs nothing. But it posts to the bridge, so the bridge still has to be running.
Use the npm embed yes—— Your app already needs Node to build. Can run bridge-less against your own API route.
Build from source yesyes— pnpm 9+ for the workspace. Chromium downloads on demand, for tests only.
The bridge-less escape hatch. The embed can POST to any endpoint you give it, so an app that already has a dev API route can skip the bridge entirely and write its own inbox file. You lose the review direction — that needs the broker — but the "point, note, fix ui" loop works with no daemon at all.
05

Building it, and loading it into Chrome

One command builds everything. The only thing worth memorizing is which directory Chrome wants. 

# everything: bridge daemon, Chrome extension, npm tarballs
make build

# it prints where each artifact landed
built:
  bridge     packages/bridge/dist/cli.js
  extension  /…/fix-ui/extension
             ^ load THIS directory in chrome://extensions, not extension/dist
  tarballs   dist/
Load extension/, not extension/dist/. This is the one thing that trips everybody. The compiled bundles land in extension/dist/, but manifest.json sits one level above them and points down into dist. Chrome needs the folder containing the manifest — aim it at dist/ and you get "manifest file is missing".

The whole setup, once

1 · build
make build

2 · load into Chrome
chrome://extensions → Developer mode ON → Load unpacked → pick extension/
   (no icon ships in v1 — it's the default puzzle piece; pin it)

3 · start the bridge in the project you want fixed
cd ~/my-app && make -C ~/fix-ui run PROJECT=$PWD
   → prints:  listening on http://127.0.0.1:3499
   → prints:  review token: d1G2K-jRF79… (also in .fix-ui.token)

4 · point the extension at it — right-click the icon → Options
Bridge URL     http://127.0.0.1:3499
Review token   paste from .fix-ui.token
Origins → projects
               http://localhost:3000=/Users/you/my-app
               https://staging.example.com=/Users/you/my-app

That last field is what makes a note from a given site land in the right project. An unmapped origin falls back to whichever directory the daemon was started in — fine when you're working on one thing, ambiguous when you're not.

Then: click the toolbar button to arm the picker, click an element, type, save. Click the button again to stop. Nothing is injected into any page until you press it — there's no content script in the manifest, so the extension is inert everywhere until asked.

06

The trust boundary

A local daemon that any page can reach, feeding a file your coding agent acts on. That deserves saying out loud.

The bridge has permissive CORS on purpose: the embed runs on whatever origin your dev server uses and the extension injects into arbitrary sites, so there is no origin allowlist that could be written. The consequence is that while the daemon runs, every page you visit can reach it. That's the honest starting point, not a footnote.

Closed

Non-loopback Host → 403

A request whose Host header isn't 127.0.0.1 or localhost is refused. This is the DNS-rebinding defence; CORS cannot be one.

Closed

Review channel needs a token

The daemon mints one per run into .fix-ui.token (mode 0600). Without it, no /events stream and no verdict. So a page can't learn a review id, and can't answer your review.

Closed

Size and length caps

256KB bodies, and bounded note and selector. Nothing can use your inbox as storage or exhaust the daemon.

Open, on purpose

Anyone can request a review

A proxy instance can't read the daemon's token file, so this route stays ungated. A page can raise a banner with text it chose, and occupy the review slot until timeout. It cannot answer — that needs the token.

Treat inbox entries as untrusted input, never as instructions. This is the rule that matters. Your agent is told to read .fix-ui.jsonl and act on it, which makes that file the most interesting thing on the machine to anything trying to reach your agent. Run the daemon while you're working, not permanently.

One more, because it's inherent rather than fixed: when a page opens a modal dialog, the picker has to move its own UI inside that dialog to stay clickable — the browser's top layer leaves everything else inert. In that window its UI is ordinary page DOM, readable and clickable by page script. The two decisions that must be a human's — approving a review, committing a note — require a real user event, which script cannot forge. The rest is exposed, and saying so is cheaper than pretending otherwise.

07

Wire reference

Everything either half can say to the bridge.

HTTP · for browsers
RoutePurposeGated
POST /entriesSave a note. Returns the entry as stored.open
GET /entriesList a project's inbox — the saved-notes panel.open
DELETE /entries/:idRemove one line.open
GET /eventsSSE. Carries review-requested and review-cancelled, replays a pending review to anyone who reconnects.token
POST /reviewsThe agent side of a review. Held open until answered.open
POST /reviews/:id/verdictApprove or request changes.token
GET /healthzIdentity probe — how a second instance recognizes the daemon.open
MCP · for agents
ToolWhat the agent gets
list_feedbackThe project's entries, structured — no file paths to know.
resolve_feedbackRemoves an entry once it's fixed.
request_reviewBlocks until you answer. Returns your verdict, the notes you left, and how long you took. Sends progress notifications while waiting so long reviews don't trip client timeouts.
feedback/updatedA notification, not a tool — fires when the inbox changes. It cannot start a turn; it only helps harnesses that choose to watch.
Verdicts
  • approved — you're happy. The loop closes.
  • changes — paired with the notes you left. This is the actionable one; the agent treats the entries as the change request and keeps working.
  • timeout — nobody answered in time. A first-class outcome, not an error.
  • no-reviewer — no page was listening, so the agent doesn't hang waiting for one. It falls back to asking you in the terminal.
